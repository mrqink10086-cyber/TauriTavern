# 状态

> 状态系统的整体形态、配置入口与设计红线见[状态系统](StateOverview.md)；本文是规范正文：声明、键、访问三态、注入、楼层版本、面板、接口与边界。

状态是聊天中随剧情变化的事实：时间、地点、在场角色、着装、关系与好感度。它有两个用途——进入模型上下文（注入），以及在界面中呈现（面板）。

状态不新增一套存储与注入机制，而是复用已有的两条链路：世界书的求值与注入，工作区的持久与版本。

需要"故事走到哪一步"这类位置语义时，上面可以叠一层可选的[状态机](StateMachine.md)：它复用同一份声明与同一份存储，只负责位置之间的移动，不改动本文的存储语义。

分工是：**字段由用户声明，权限由用户逐字段配置，条目与状态的取舍由代码确定性求值，更新由配置指定的执行者提交。**

## 状态是动态条目

世界书条目表达作者写好的设定，状态表达模型在本轮产生的事实。在读取侧，二者是同一种东西。

| 维度 | 静态条目（世界书） | 动态条目（状态） |
| --- | --- | --- |
| 内容 | 用户编写 | 模型填写 |
| 变化 | 跨轮不变 | 每轮可变 |
| 定位 | 条目 uid | 声明中的字段路径 |
| 作用域 | 触发键、角色与 tag 过滤 | 逐字段访问配置 |
| 注入 | 位置、深度、顺序、预算 | 同一套语义 |

因此两者共用求值器与注入管线，只在**持久化与写入路径**上分开：世界书保留 ST 兼容的文件布局与编辑器，状态使用独立存储与 Run 生命周期。

同一个字段同时存在静态与动态值时，**动态覆盖静态**。状态表达更近的事实，不能让用户写死的旧值盖住它。

## 状态声明：字段由用户定义

状态字段不由模型自由发明。用户先声明一份清单，说明这个聊天需要跟踪什么。

| 声明项 | 说明 |
| --- | --- |
| 类别 | 顶层分组，同时作为面板页签。**名称由用户定义，域层不预设任何类别** |
| 主体 | 需要按聊天对象展开的层级，例如按在场角色；不需要主体的类别可以省略这一层 |
| 分组 | 主体下的子分组，如 `着装` |
| 字段 | 最小跟踪单位，也是权限配置的最小单位 |
| 显示名 | 面板上呈现的文字，与字段路径解耦 |
| 呈现方式 | 单值文本、多值标签列表、数值条 |

**层级与命名全都属于声明。** 域层只拒绝结构上不可用的 key——空段、控制字符、过深、过长——不枚举任何类别名、不规定固定深度。上一节 JSON 里的 `环境` / `角色` / `模式` 只是一份示例声明，不是约定。

声明承担三件事：

1. **校验依据。** 未声明的字段一律拒绝，模型不能自造状态。这比"前缀白名单"严格得多。
2. **面板结构。** 页签、分组、条目顺序全部来自声明，界面不需要猜。
3. **配置清单。** 访问配置界面逐项列出这些字段——没有声明就无法提供逐字段配置。

### 场景文件：可导出、可导入

声明既然是完整的一份场景，它就能**作为一个文件离开这台机器**——这包括字段、面板、HTML 模板、主题 CSS、共享脚本、机器与谓词集。手感上这是最直接的一条路：让别人写的场景进来，不用在表单里逐行重敲；面板的样式也不用靠手写。

文件带一个头部，好让导入能判断自己在读什么：

```json
{ "kind": "tauritavern.state-declaration", "version": 1, "name": "scene", "declaration": { … } }
```

| 规则 | 说明 |
| --- | --- |
| 文件类型由 `kind` 判定 | 不是这个 `kind` 就拒绝，不做"看起来像声明就试着读"的猜测 |
| 版本只接受 ≤ 当前 | 来自更新版本的文件可能带本版本不认识的键，静默丢掉等于吃掉半个场景 |
| 名字来自文件 | 同名已存在时**先问再覆盖**——导入是场景进来的方式，不是场景消失的方式 |
| 导入后仍要保存 | 文件里的声明照常过后端校验，失败就是用户看到的那条消息 |

### 一份声明就是一个场景

一场戏对作者来说是一件事：**跟踪什么、怎么显示、什么让它变化**。所以机器（阶段推进）与谓词集（条件注入）可以直接写在声明文档里（`machine` / `predicates` 两个可选键），随声明一起保存、导出、绑定：

| 键 | 内容 | 缺省 |
| --- | --- | --- |
| `fields` | 字段清单；每行还带着这个字段对每个 Agent 的默认三勾 | 必填 |
| `panels` | 显示方式：面板、图片候选、HTML 模板、共享脚本、主题 | 空 |
| `machine` | 这个场景的阶段推进 | 无阶段 |
| `predicates` | 这个场景条件注入的说明条目 | 无条件注入 |

**向后兼容的解析顺序**：声明自带 `machine` 时，它就是本聊天的机器，单独绑定的机器不再参与；声明没有时，才回落到单独绑定的那份。谓词集同理。两者都存在时不会合并——两份规则加起来会让"哪条在生效"无法回答。

**保存时一起校验**：声明里的机器与谓词集在保存声明时就走各自的结构校验，写进文档的规则不会是一份存得下来却跑不起来的配置。

声明按聊天绑定，解析顺序沿用主题的既有模式：聊天绑定 → 角色/群组绑定 → 全局默认。用户可以保存多套方案复用。

## 键的写法与匹配

声明里的每个字段都要写成一个**键**。这里有三处"匹配"容易被混为一谈，但它们的匹配对象根本不同，语义也必须不同：

| 用途 | 匹配对象 | 语义 |
| --- | --- | --- |
| 世界书条目 key | 大段聊天文本 | **包含匹配**：文本里出现即命中 |
| 声明键 | 键字符串 | **锚定全匹配**：整串等价才算命中 |
| 调用方给的键 | 键字符串 | **机械归一 + 唯一性判定** |

**锚定是硬约束。** 世界书正则在聊天文本里搜索，所以"包含即命中"是对的；而声明键做的是"这个键归哪个字段"的**归属判定**——`环境/日期` 与 `环境/日期/来源` 是两个不同字段。若照搬包含语义，`环境/*` 会顺带命中它下面所有子字段，注入与可写范围被静默放大。实现上一律编译成 `^(?:body)$`。

### 三种写法

| 写法 | 例子 | 含义 |
| --- | --- | --- |
| 字面 | `环境/日期` | 就是这个字段 |
| 通配 | `角色/*/着装` | `*` 覆盖**一个**段，`**` 覆盖**一层或更多**层（不含零层） |
| 正则 | `/(日期\|时间\|时刻)/` | 逃生门，沿用世界书既有的 `/pattern/flags` 形式 |

正则形式接受 `i`（大小写不敏感）与 `u`（Unicode，恒为开）；`g` / `y` 是 JS 专有且在此无意义（键始终锚定、只匹配一次），报错并说明原因；其他 flag 一律拒绝。body 内的 `/` 必须写成 `\/`，否则定界有歧义。

**不引入宏。** `{{char}}` 会带来"何时展开"的问题——保存时展开会锁死当时的角色，匹配时展开则要把宏引擎带到后端；而捕获组天然没有这个时刻，`角色/*/着装` 一个模式覆盖所有角色。少一个机制。

### 容错：只做机械归一，不做猜测

调用方给的键先过一遍机械归一，全部是可逆、无歧义的变换：

| 步骤 | 例子 |
| --- | --- |
| 全角 → 半角 | `环境／日期` → `环境/日期` |
| 反斜杠 → 斜杠 | `环境\日期` → `环境/日期` |
| 空白：首尾、段内连续、空段 | ` 环境 / 日期 / ` → `环境/日期` |

归一之后按两级匹配，前一级有结果就不进入下一级：**先原样精确比较，再大小写折叠**。因此一份刻意同时声明 `HP` 与 `hp` 的清单仍然精确解析，而 `Hp` 这种只折叠后同时撞上两者的拼写被判为歧义并拒绝——**不猜**。

**明确不做**：找最相近的字段（编辑距离、相似度打分）。那会让未声明的键被静默映射到某个已声明字段，状态被污染且无人知道；模型也会学会"随便写反正会被猜对"，正好抵消错误回灌让它一轮改对的机制。需要容忍什么变体，由用户用通配或正则**显式**表达。

### 归一之后写入哪个键

| 命中的是 | 存储的键 |
| --- | --- |
| 字面项 | **声明里那个名字**（调用方的拼写漂移被拉回） |
| 模式项 | **调用方给的键**（通配处正是由它选择的地方） |

这条区分让状态文档永远只有规范拼写，不会因为漂移长出两个同义字段。

### 重叠在保存时检测

`环境/*/来源` 与 `环境/日期/来源` 都能接受同一个键。这是配置错误，不该在运行时猜。声明保存时检测并拒绝：

- 两个字面同名
- 字面已被某个模式覆盖
- 两个模式可能相交（逐段保守比较，`**` 按"一层或更多"展开）

`/pattern/flags` 逃生门**不参与结构比较**——自由正则的相交性无法一般判定，硬猜只会误报。用了正则的声明项需要用户自己保证不与他项重叠；字面项与它的冲突仍然精确可查。

## 每楼一份聚合状态

状态以**一次工具调用**提交：

```json
{
  "fields": [
    { "key": "环境/日期", "value": "2026/09/10" },
    { "key": "环境/时间", "value": "下午" },
    { "key": "环境/地点", "value": "某处公共场所" },
    { "key": "角色/角色甲/标签", "value": ["标签一", "标签二"] },
    { "key": "角色/角色甲/着装/上装", "value": "浅色外套" },
    { "key": "角色/角色甲/着装/鞋子", "value": "平底鞋" }
  ],
  "remove": ["角色/角色乙/着装/帽子"]
}
```

**上例中的键名只是占位。** 键空间完全由你的声明定义：类别叫什么、分几层、有没有"角色"这一层，都由你决定。

**key 是路径。** 用 `/` 切分层级，与声明的层级一一对应。不在声明中的 key 直接拒绝。

**三态语义必须显式区分**，这是本设计最容易出错的环节：

| 情况 | 语义 |
| --- | --- |
| key 未出现在 `fields`，也不在 `remove` | **保持原值不变**（这就是增量） |
| `value` 为空字符串或空数组 | **清空**该字段的值 |
| key 出现在 `remove` | **删除**该字段 |

不允许用空值表示删除。空值是合法状态，删除必须显式表达。

## 状态访问：逐字段三勾

颗粒度是**声明里的每一个条目**，不是类别或分组——条目本身可以是字面键，也可以是 `角色/*/着装` 这样的模式。

**默认写在字段上，例外写在 Profile 里。** 每个声明字段带着自己对每个 Agent 的三勾默认（`DeclaredStateField.access`），Profile 的访问行是覆盖：

| 能力 | 含义 | 字段默认 |
| --- | --- | --- |
| 注入 | 该字段的值推入该 Profile 的上下文，无需工具调用 | **开** |
| 可见 | 该字段可经工具检索与读取，但不自动进入上下文 | 关 |
| 可写 | 该字段可被更新 | 关 |

**为什么注入默认开、另两个默认关。** 三勾不是同一类东西：注入是"这个字段存在、模型该知道它"，把字段写进声明就已经表达了这件事，再让用户为每个字段勾一遍是重复劳动；可见与可写是**额外授权**——前者允许模型在任意回合主动拉取，后者允许它改写值——不该由"写了这个字段"顺带给出。所以默认阅读姿势是：**声明即注入；要拉取或改写，去 Profile 里给哪一行。**

解析顺序（`resolve_access`）：**能匹配上的 Profile 行 → 声明字段的默认 → 都没有则用 Profile 自己的答案**。第三条只在"聊天没有任何声明"或"这个键不属于任何声明字段"时出现，也就是没有字段可问的时候。

**Profile 行是双向例外**：加了一行，那个键此后只听这一行的，没勾的就是不给——既能把字段默认不给的权限给出去，也能把一个默认注入的字段静音。默认 Profile 没有任何行，因此默认行为完全由字段决定。

**代价要清楚**：注入是每轮都花上下文的那一个。字段清单长（几十个字段）时，默认全开会把每轮前缀撑大；该沉默的字段（只在特定场景用的）就在 Profile 里加一行把它静音，或者干脆不声明。

| Profile | 典型配置 |
| --- | --- |
| 主 Agent | 不加行（声明即注入）；少数数值字段加一行把 `注入` 收回去，避免角色"演数值" |
| 负责更新状态的执行者 | 加行给要维护的字段：`可写`；需要主动检索时再加 `可见` |
| 特定读者（如只关心着装） | 一行 `角色/*/着装`：注入；其余不勾 |
| 数值计算 / 纯校对 | 需要的字段留默认或只给可见，写入相关勾全撤 |

**谁会被标记为"该写没写"。** 楼层上的"这楼状态没更新"记号按同一套解析判断（`has_writable_access`）：只要字段默认或 Profile 行里有一处允许写，就期待这一楼写出状态；两边都不允许写的聊天不会有这个记号。默认字段是可写关，所以"没有任何 Profile 行"的聊天不会被标记——没有谁被授权写，也就没有谁迟到。判据是聊天级而不是键级——标记说的是"这一楼"，不是"某一个键"。

**为什么必须细到字段。** 有些状态会影响角色代入。好感度数值、幕次标记、系统提示性质的信息一旦进入主 Agent 的上下文，角色会开始"演数值"而不是"演人"。所以注入必须能精确到单个字段——默认按"声明即注入"走，需要沉默的字段由 Profile 行逐字段收回。

**可见的门槛比注入更高。** 注入是一次性的、位置固定的、可以预算的；可见意味着模型可以在任意回合主动检索，代价和副作用都更难估计。所以可见默认不给，通常只给负责更新状态的执行者。

注入与可见是"推"与"拉"，互不依赖。

配置按 Profile 存放（`AgentProfileDefinition.stateAccess`，与画像同文件持久化），按字段路径索引。

规则：

- 解析为不可写的键，写入请求被拒绝，返回可定位到字段的可恢复错误。
- 解析为不注入的字段不进入上下文；若解析为可见，模型仍可经工具检索。
- **负责更新状态的执行者必须看得到它要维护的字段**：本地模型实测（`scripts/state-tool-probe.mjs` C 段）——只声明、不注入的字段，模型不会去写它；它会尽力把变化塞进看得见的字段里（例如把时间变化并进日期字段）。准入是双向的：挡住一个字段的注入与可见，也就挡住了它的更新。

## 状态谓词条目

内容固定、但**是否生效由状态决定**的条目（例如「好感度 51–80 时的行为指导」），不是普通世界书条目。它除了激活自己，还要能作用于其他条目。

### 三种激活输入

| 激活输入 | 依据 | 例子 |
| --- | --- | --- |
| 文本触发 | 对话文本里的关键词 | 普通世界书条目 |
| 状态谓词 | 状态字段的值 | 好感度 51–80 → 「表现亲近」 |
| 恒常 | 无条件 | 世界书设定条目 |

普通条目天然可叠加，多条同时注入并不冲突。谓词条目相反：同一时刻不能既「保持疏离」又「表现亲密」，因此必须有组内互斥。

ST 世界书的 inclusion group 不能直接复用：它是对已通过关键词激活的候选做去重与加权选择，**输入仍是文本匹配，没有谓词**，表达不了"按数值区间切换"。

### 可用性：条目不适用时应当不存在

条目可以声明自身的适用前提。前提不成立时它**不进入候选集**，而不是"存在但被压掉"。

身体部位类条目是典型：角色没有尾巴时，「尾巴」相关条目根本不该出现。

不可用与被抑制都表现为"不注入"，但原因不同，界面与调试必须能区分——前者是条目不适用，后者是条件成立但被其他条目压掉。

### 效果：条目可以作用于其他条目

激活的条目或组可以声明对其他条目的效果：

| 效果 | 含义 |
| --- | --- |
| 抑制 | 本条生效时，被选中的条目不注入 |
| 要求 | 本条生效时，被选中的条目必须存在，否则本条不生效 |

选择器按**标签**匹配，不按条目 id。用户写的是"处于依恋阶段时抑制所有标为『距离感』的条目"，而不是逐个列出条目。因此条目需要自己的标签，它与角色的 tag 不是一回事。

### 覆盖关系由代码判定

旗舰模型或许能读出"这两条互斥、那条已经过时"，但它**分不清覆盖的方向**：谁压谁、谁先失效。这是纯确定性的问题——在代码里明确设定就一定分得清。

求值分四步，每步都是确定性的：

1. **收集候选**：文本触发、谓词求值、恒常条目，并剔除不可用条目
2. **应用效果**：抑制与要求，迭代到收敛（效果之间可能相互影响）
3. **组内互斥**：每组恰好一条，按优先级取一条，其余移除
4. **排序与预算**：按位置与优先级排序，再按 token 预算取舍

**输出是一份"最终生效集"。模型只看到结果，不做任何覆盖判断。** 过程可记录、可解释、可复现。

组内互斥由求值保证，而不是靠用户把条件区间写对。区间写重叠时的表现是"优先级决定谁生效"，不是"两条同时注入"。

### 与状态声明的引用关系

谓词与可用性都引用状态字段，因此[状态声明](#状态声明字段由用户定义)同时是谓词的**合法字段白名单**。引用未声明字段属于配置错误，保存时拒绝，不进入运行时。

### 永不落盘

这类条目**只在组装提示词时由「状态 + 声明 + 条目定义」合成，不写入世界书文件或聊天 metadata**。

落盘就会引入替换问题：写入新条目与删除旧条目是两个动作，中间失败或漏删会留下并存的两条，而且是持久化残留——重启也不消失。不落盘就没有可残留的副本，替换退化为重新求值，天然原子。同理，这类条目不进向量索引，避免切换后旧条目仍被召回。

## 状态更新的执行者

状态需要被更新，但**由谁执行不由本设计规定**。Run 配置里指定执行者，可以是主 Agent，可以是某个子代理，也可以是模型之外的手段。

设计只规定三件事：

- **谁能写**：逐字段的可写授权
- **写什么**：一次调用提交的字段集合
- **写了之后怎么用**：版本化并按楼绑定，供谓词求值与注入消费

**接受滞后，不接受不确定。** 状态可以落后正文一轮甚至更多——这在角色扮演场景里可以接受，需要更精确规则的用户可以在自己的提示词里补充。但谓词求值使用的状态必须是**某一个确定版本**，不能是"可能仍在更新"的中间态。

## 写入

写入是一次工具调用，不是逐字段写文件。

**为什么不是多文件。** 逐字段写文件需要 N 次调用：消耗 N 次工具预算（默认每 Run 80 次）、产生 N 组事件与 `tool-args/`、`tool-results/` 文件，并且 N 次独立写入无法保证原子性——中途失败会留下半个状态。一次调用只消耗一次预算、产生一条事件，并且结果是一个整体。

**校验分两层，都发生在写入时：**

1. **声明校验**：key 是否在用户的声明中，值是否符合该字段的呈现方式
2. **访问校验**：调用方 Profile 是否对该字段标记为可写

校验失败返回**一次列出全部字段错误**的可恢复结果，模型一轮即可修正。错误必须可定位到具体字段，不用笼统的"格式错误"。

写入落在 Run 工作区的状态目录，Run 成功提交时发布为持久版本。

### 首楼播种：一个聊天从哪开始

一个聊天在没有任何状态文档之前，第一楼的状态**不是空的**，而是声明里写下的初始值（`DeclaredStateField.initial`）：`环境/日期 = 2026/09/10`、`环境/地点 = 咖啡馆`。理由很实际——不播种的话，模型得先把每个字段都写一遍，故事才能开始；面板在没有写入之前也只能是一片空白。

| 规则 | 说明 |
| --- | --- |
| 只在**没有**文档时发生 | 文档存在（哪怕字段被删光）＝这个聊天真实到达的状态，播种会把它抹掉 |
| 只有**字面键**能带初始值 | 通配还没有确定的键；给它播种等于替调用方发明键名——这正是声明要防的事 |
| 保存时校验，不裁剪 | 空值、超长、条数超过 32 都在保存声明时拒绝（`state_declaration.invalid_initial`），不静默丢 |
| 不过 `StateAccess` | 它不是模型的写入，而是"这个场景开始时就有的状态"；和 Run 提交时的自动求值同一理由 |

### 界面写入：人点一下也是一次写入

模型用工具写，人用面板写。两条路走到同一个地方——一个已发布的、绑在某一楼上的版本——并且都过同一份声明校验。差别只有两点：

| | 模型写入（`state.update` / `state.transition`） | 界面写入（`update_state_values`） |
| --- | --- | --- |
| 授权 | 过 `StateAccess`：这个 Profile 的模型能写什么 | **不过**：点一下不是模型自作主张，声明校验仍然过 |
| 触发 | 模型决定要改哪个键 | 人改完那个键，还期待派生值跟着变 |

**派生值跟得上，靠的是同一个脚本。** 界面写入之后可以再跑一次场景机器的脚本钩子（`reason: "recalculate"`），让日历、总额、装备加成这类"引擎不该知道公式"的值跟上这一次改动，并且写进**同一个版本**。也就是说：一次点击最多产生一个版本，里面既有人的改动，也有脚本算出来的结果。

**新版本必须绑到楼层上。** 写入命令返回新的 `stateId`，前端把它写进它所属楼层的 metadata（`bindEditedStateToFloor`：最近一个已经带状态的楼层，聊天里一份状态都没有时就是最后一楼）。没绑定的版本会被发布然后立刻看不见——这正是这条路径最不能有的静默失败。

**面板上的铅笔是唯一入口。** `state-panel-ui.js` 给每个文本字段一个编辑入口（保存 / 清空 / 删除 / 取消），图片字段不给：图片是状态选出来的结果，用输入框改写它比让机器去改更糟。有编辑器打开时面板会撤掉 `aria-hidden`——那会儿它是表单，不再是装饰。

## 注入

注入出去的是**文本行** `名字: 值`，不是 JSON，也不是键路径清单（`render_injection`）。名字的取法有一条窄规则：

| 情况 | 注入成 | 例子 |
| --- | --- | --- |
| 声明把键写成字面量，且这个名字不会和别的字段撞 | 显示名 | `日期: 2026/09/10` |
| 键是被通配/正则覆盖的 | 键路径 | `角色/甲/好感度: 42`——路径里带着"是谁"，标签说不出来 |
| 两个字段的显示名相同 | 两条都用键路径 | 名字不能同时指两件事 |

值里重复出现的同一串只说一次（`["白天","白天"]` → `白天`），首现顺序保留，所以同一份文档永远渲染出同一段文本。

状态的**位置**由变化频率决定，不由重要性决定。原因是前缀缓存：

- 静态内容（system、世界书）跨轮不变，放在前缀区可以长期命中缓存
- 动态内容放在前缀区，会**每轮击穿整段前缀缓存**，长上下文下成本成倍上升

因此：

| 示例状态类别 | 变化频率 | 注入位置 |
| --- | --- | --- |
| `环境` | 每轮可能变 | 最靠后（末尾前固定深度） |
| `角色/*/着装`、`模式` | 中频 | 中段 |
| 长期设定（外貌、关系基调） | 低频 | 可进前缀区，当作 constant 条目 |

注入内容先按该 Profile 标记为**注入**的字段过滤，再渲染。同一个状态，不同的执行者按各自勾选看到不同切片——勾了全部字段的执行者看到全貌，只勾几个字段的读者只看到那几个。位置、深度与 token 预算与世界书条目共用同一套字段，只是取值不同。

**落位的具体分工（已实现）**：位置由字段默认与**访问条目**上的 `injectSlot`（`before` / `after` / `atDepth`）与 `injectDepth` 决定，默认 `atDepth` + 深度 4——高频低风险的默认值：靠近末尾，不击穿前缀缓存。后端按「注入」解析结果过滤、以**键序**渲染成 `键: 值` 行、按槽位合并成块（同一槽位与深度合成一段文本），前端在组装提示词时用与世界书相同的扩展提示机制落位（`before` → 主提示词前，`after` → 主提示词后，`atDepth` → 距末尾 N 条消息）。注入的来源是**字段默认（开）+ Profile 行（可正可负）**：没有任何声明与访问配置的 Profile 注入零块（没有字段，也就没有可注入的东西）；声明了字段就注入，要沉默某个字段由 Profile 行收回。世界书与状态共用槽位但键名不同，因此不会互相覆盖：同一深度上两者按登记顺序拼接（世界书的深度注入先登记，随后是本模块的状态块）。

## 楼层与版本

状态按楼层保存：**每楼一份聚合状态**，而不是每楼一组字段文件。一份文档正好落在既有的**单文件原子发布**保证上，不需要新造目录级原子性。

楼层绑定的是**该楼产生的状态**。因此面板读**最后一楼**绑定的版本即为最新状态；"读到的状态"可从上一楼推导，信息不丢。已有持久版本目录与消息 metadata 的绑定机制可直接沿用。

**重新生成与删除楼层**取该楼绑定版本的快照，无需回放。持久版本按既有保留窗口清理。

## 显示：左右停靠栏面板

面板挂在聊天列两侧的**停靠栏**（rail）里，不进入聊天流布局。因此它不引起聊天容器重排，也不参与消息虚拟化——不会被消息卸载带走，也不需要在消息流增长时重定位；窄屏收起为边缘把手。

必需能力（均已实现，落地形态见右列）：

| 能力 | 说明 | 落地形态 |
| --- | --- | --- |
| 位置持久化 | 拖动后的位置写入本地设置 | 拖栏内缘的**抓手**调栏宽，写在浏览器本地（`tauritavern.state-panel.view`）——它是本机偏好，不是状态，所以不进声明：同一份声明在手机与宽屏上需要的宽度不同 |
| 折叠态 | 可缩为标题栏；否则遮挡正文 | 点面板标题折到标题栏（逐面板记住），抓手与面板同级、直接子元素结构不变 |
| 边界约束 | 不可拖出可视区，窗口缩放时夹回 | 栏宽夹在 `[96px, min(可用宽 × 40%, 可用宽 − 320px)]`，另有 560px 绝对上限（量不到可用宽时只受它约束）；窗口 resize 重新夹 |
| 移动端降级 | 窄屏退化为可折叠的底部抽屉 | 沿用既有的 768px 断点与 safe-area 契约；窄屏下抓手不再调宽而是收起/展开（该行为**只在窄屏布局生效**，否则宽屏上没有第二个控件能把栏取回来） |

拖动**只移动抓手**（写 `transform`），栏宽在松手时提交一次：拖动热路径里没有任何测量、夹取或重排——这正是"几何重算排除在拖动热路径之外"的落地方式。

移动端复用既有的 `data-tt-mobile-surface` 分类与 safe-area 契约，不另写一套几何规则。拖动时只写 `transform`，几何重算排除在拖动热路径之外。

面板只在**该聊天存在状态数据且未被隐藏**时出现。

**面板来自声明——没有声明就没有面板。** 键空间与显示名都来自状态声明；面板显示数据而不是 schema：只有该楼状态文档里**确实存在**的字段会出现在面板上——声明了但从未写过的字段不占一行空行；没有数据的面板不存在。未配置面板时按声明的顶层键段自动派生（每段一个面板、左栏、文本渲染），因此没配置过的聊天也有可用面板。

**图片是候选集，不是固定文件。** 面板背景与字段图都可配置多张候选，每张带一个条件；求值取**声明顺序里第一个条件成立者**，无条件的候选是兜底、必须排在最后（排在中间会让后面的候选永远选不中，保存时拒绝）。没有候选命中就**不显示图**，这不是错误；但**条件里的 `op` 未注册是错误**——否则会显示一张没有任何条件选中的图。

**条件词汇表就是状态机层那一套**（`ConditionSpec` + `ComparatorRegistry`，`tt-domain` 的 `evaluate_condition` 是它的单条件入口）。两个含义几乎相同的条件语言一定会漂移，所以面板、谓词条目、状态机共用同一个词汇表与同一份 `op` 注册表。**一个条件放不下时用组合，不用脚本**：`ConditionSpec` 可以自带 `compose`（`all` / `any` / `not`），"夜晚 且 下雨"是配置不是程序；组合按同样确定性的规则求值，`op` 未注册照旧报错（哪怕别的分支已经成立——配置错了就是错了），空组合与"既比较又组合"的节点在保存期拒绝。

**条件表达不了的选择可以写一段脚本**：候选集上的 `conditionScript`，类型与状态机的钩子同一个（`ScriptSpec`，内联在声明文档里，因此随文档一起导入导出，不需要第二个存储）。**留空即默认**：按上面的条件按序选择；**写了脚本就由脚本决定**，那些条件不再参与——两者同时生效会让显示的图取决于调用方先应用了哪一个。脚本在 Skill 脚本沙箱里执行，拿到 `{ state, candidates }`，返回 `{ index }`（`null` 表示不显示图）；下标越界或形状不对是错误（`state.panel_script_invalid`），脚本抛错是错误（`state.panel_script_failed`），两者都**不静默退回条件**。编辑器在脚本生效时显式提示"上方条件不参与选择"，免得调试用的脚本被忘掉后条件悄悄失效。**应用层执行脚本并把结果写回配置**，域层保持零引擎：它看到的仍是一个普通候选集。

**多张图共用一套规则时，逻辑写一份**：面板配置带一个共享模块表（`panels.scripts`，模块名 → 源码），候选集的脚本可以 `import` 它，于是每个候选集只剩一行 `import { pick } from './scene.js'; export default pick;`。模块名**必须是扁平的 `name.js`**——那正是入口脚本里 `./name.js` 解析到的名字，带路径会让同一句 import 在不同入口下含义不同。共享模块的源码与入口一起进沙箱，入口不能被同名模块顶掉（调用方要跑的就是入口）。

**图片来源限定为宿主已服务的主机路径**（`/backgrounds/...`、`/user/images/...`、`/assets/...`），拒绝 scheme 与路径穿越：面板在应用自身源内，不能指到任意文件或外部站点。

**字段图有两种来源**：字段值本身就是图片路径（`render: image`），或由候选集按状态选择（配置了候选集时优先，值保持自己的含义）。PNG/JPG 与既有的图片白名单一致（`user_media_service.rs` 的 `MEDIA_EXTENSIONS` 已含 `png/jpg/jpeg/webp`）。

**面板的可见性与模型准入无关。** `StateAccess` 三态说的是"某个 Profile 的模型"能看到什么；面板是**用户看自己的状态**，不按 Profile 裁剪。面板显示什么由面板配置决定：没放进任何面板的字段不显示。

**样式分三层，后一层只写与前一层不同的部分**：内置默认样式（`src/css/state-panel.css`，类名契约见其文件头）→ 主题 CSS（声明里的 `panels.css`）→ HTML 模板（`StatePanelSpec.markup`）。后两层都在**保存时编译**：主题被解析并作用域化到 `.tt-state-root`，模板被解析成节点树；渲染期只贴文本、只按树创建，没有任何解析——细节见[阶段 3c](#阶段-3--面板与配置界面)。

## 配置界面

这一部分必须和状态功能一起做：声明与权限都靠用户维护，没有界面就无法使用。

| 界面 | 内容 |
| --- | --- |
| 状态声明 | 编辑类别、分组、字段、显示名与呈现方式；保存为方案，按聊天绑定 |
| 访问配置 | 按 Profile 列出条目，每条一行三勾（注入 / 可见 / 可写）与落位；支持批量添加键模式 |
| 谓词条目 | 编辑条目组、谓词、可用性前提、效果与标签；预览求值结果 |
| 面板设置 | 左右栏归属、面板标题与匹配的键、字段的显示名与渲染方式（文本 / 图片）、背景图与字段图的候选集（多选 + 条件）、折叠与隐藏 |

访问配置的界面形态沿用既有的"工作区访问"面板：每行一个条目，每行若干勾，条目有三勾而不是两勾。**已实现的部分**（`ProfileStateAccessSection`）：每行一个键模式 + 三勾 + 落位（`before` / `after` / `atDepth`）与深度，外加"批量添加"——一行粘贴逗号分隔的键模式，每个展开成一行，逗号切分识别 `/pattern/flags` 段（正则里的逗号不会被切断）。保存时空白行使被丢弃，落位与深度等于默认值时不写进文档。

**与上文"条目来自状态声明"的差异要说明**：画像是与聊天无关的，而声明按聊天绑定，所以网格不预设字段清单——用户粘一列键即可。**两种展开都已实现**："从已保存的声明展开"与"读当前聊天绑定的声明并展开成行"（后者需要画像面板解析聊天 → 角色/群组 → 声明的绑定链；扩展侧适配器 `chat-state-declaration.ts` 沿用运行路径同一绑定策略，解析不到时不发明绑定），并支持**按类别/分组折叠**（按模式顶层键段分组，折叠与编辑都不移动数据）。

谓词条目需要一个**求值预览**：给出一个假定状态，显示"最终生效集"以及每条被移除的原因（不可用 / 被抑制 / 组内未选中）。这是让用户确认覆盖关系的最直接手段。

## 接口

**工具**

- `state.update(fields, remove)` — 提交状态更新；字段未标记可写时拒绝。工具名在模型侧写作 `state_update`（命名空间点号转下划线）

**后端**

- `StateDeclaration` — 用户声明的字段清单，按聊天绑定；保存时校验键模式重叠
- `StateKeyPattern` — 声明键的三种写法：字面 / 通配 / `/pattern/flags`
- `KeyResolution` — 一次键解析的结果：命中 / 未约束 / 未声明 / 歧义 / 不可用
- `normalize_key` — 机械归一（全角、分隔符、空白），不含任何猜测
- `StateDeclarationRepository` — 声明方案的命名存储（`user_dir/state-declarations/<name>.json`）
- `StateDeclarationService` — 保存校验（名字合法性 + **重叠在保存时拒绝**）与薄转发

**命令与路由（已注册）**

- `save_state_declaration` / `get_state_declaration` / `list_state_declarations` / `delete_state_declaration`
- 前端路由：`/api/state-declarations/{save,get,list,delete}`
- 注入：`get_state_injection(chatRef, stableChatId, profileId?)` — 从聊天最后一条带 `persistStateId` 的消息定位最新已提交版本，读该版本的 `state/document.json`，按 Profile 的访问配置过滤并渲染；前端路由 `/api/state/injection`
- 绑定沿用主题的既有模式：`chat_metadata.state_declaration` → 角色/群组绑定（`power_user.state_declaration_bindings`）→ 无 fallback；解析函数 `resolveStateDeclarationBinding`（纯函数，`src/scripts/state-declaration-binding-policy.js`）
- 注入：`materializeCurrentPromptSnapshot` 按解析结果把 `stateDeclaration` 放进 prompt snapshot 顶层；拿不到就不放键（后端走默认，只校验 key 形状），失败仅 warn 不阻塞 run
- `StateAccess` — Profile 上的逐字段配置：`field → { inject, visible, writable, injectSlot, injectDepth }`（`AgentProfileDefinition.stateAccess`，缺省即"尚未配置"）
- `StatePredicateGroup` — 条目组定义：谓词、互斥优先级、默认分支
- `StateEntryEffect` — 抑制与要求，选择器按标签匹配
- `StateEvaluator` — 四阶段确定性求值，输出最终生效集与逐条判定原因
- `StateRepository` — 读楼层状态、写 Run 内状态、发布持久版本
- `StateService` — 声明校验、访问校验、注入渲染、增量合并
- 命令：`get_state_injection`（**已实现**，读聊天最新已提交状态并返回按访问裁剪的注入块与 `stateId`）；`state_get_current`、`state_evaluate_preview`（未实现）；`state_get_floor` **已判定暂不需要**——聊天界面没有"停留在某个历史楼层"的概念，面板始终显示故事当前状态

**状态机层（已注册，细节见[状态机](StateMachine.md)）**

- `save_state_machine` / `get_state_machine` / `list_state_machines` / `delete_state_machine` / `validate_state_machine` / `evaluate_state_machine`
- 前端路由：`/api/state-machines/{save,get,list,delete,validate,evaluate}`
- `StateMachineSpec` / `MachineState` / `MachineEvaluation` — 定义、当前位置、一次求值的结果（含 `writes` 与 `events`）
- 命名存储：`user_dir/state-machines/<name>.json`

**前端宿主 API**

- `window.__TAURITAVERN__.api.state` — `getCurrent()`、`getFloorState(mesid)`、`getDeclaration()`、`subscribe(revision)`
- 事件：`state.updated`

**存储**

- 声明：随聊天绑定，保存为可复用方案
- 条目定义：用户维护的持久配置
- Run 内：工作区状态目录
- 持久：每楼一份聚合状态文档；版本 ID 写入该楼 metadata

## 边界

- **字段由用户定义，模型不能自造。** 未声明的 key 一律拒绝。
- **域层不枚举用户的键空间。** 类别名、层级、深度全部来自声明；域层只拒绝结构上不可用的 key（空段、控制字符、过深、过长）。任何把某个用户的字段名写进领域规则的实现都属于特判。
- **声明键锚定匹配。** 归属判定不允许包含语义，否则 `角色/*` 会顺带覆盖所有子字段，权限被静默放大。
- **容错只做机械归一，不做猜测。** 全角、分隔符、空白可修；"找最相近的字段"不可做。归一后若有多个候选，报歧义而不是挑一个。
- **域层不解析自由文本。** 键是短且强约束的标识符，可以用模式匹配；自由文本的语义永远不猜。
- **覆盖关系由代码判定。** 模型只消费最终生效集，不判断谁压谁。
- **谓词条目永不落盘。** 只在组装提示词时合成，避免替换残留与索引残留。
- **渲染期零解析。** 解析与校验只在写入时发生（每轮一次）；面板只读结构化结果。
- **不解释值的语义。** 按声明的呈现方式校验形状，不判断内容含义。
- **不静默降级。** 校验失败返回可恢复错误；该楼确实没有状态时显式标记，不伪装成继承。
- **状态更新的执行者由配置指定。** 本设计不假定由哪个 Agent 执行。
- **状态不改写聊天正文。** 状态从未进入正文，因此不需要剥离，也不会在正文里显示两份。
- **世界书的兼容契约不动。** 合并只发生在求值与注入，不触及 ST 的文件布局、uid 与编辑器。

## 落地阶段

阶段 0–6 均已实现。以下按阶段给出**每块功能的实现形态**；完整设计见前文各节。

### 阶段 0 · 状态根与版本

**实现形态**：`state` 根接入工作区宇宙（`WORKSPACE_ROOT_UNIVERSE`），按 `persist` 取持久策略，默认可见与可写范围、根目录白名单一并配置；`system_prompt.rs` 以 `state.update` 为唯一写入者给出 `state/` 目录说明，根名判定用常量（`PERSISTENT_ROOT` / `STATE_ROOT`）。

**行为**：state 目录的持久版本发布、消息绑定、swipe 起点选择与聊天分叉，与 `persist` 一致。

### 阶段 1 · 写入闭环与校验

**实现形态**：

- **纯规则层**：`tt-domain` 的键与文档规则——三态语义、批量报错、键的三种写法、机械归一与两级匹配、声明解析、歧义与重叠拒绝。落在 `models/state.rs` 与 `models/state_key.rs`。
- **工具层**：`state.update` 的 descriptor、参数解析、dispatcher 路由与默认 profile 准入。状态文档落在 `state/document.json`，单文件随 run 发布；声明从 run 输入的 `stateDeclaration` 读取，缺失时只校验键形状；写入前按工作区可写范围校验。落在 `agent_tools/state/`。
- **写入侧授权**：`tt-domain` 的 `models/state_access.rs` 提供逐字段三勾（字段默认：注入开、可见关、可写关；Profile 条目自身三勾全不勾）、锚定匹配（`角色/*` 不覆盖其子字段）、歧义与重叠的确定性判定；`state.update` 在写入前调用 `check_writable`，**解析为不可写的键整批拒绝并可定位到 key**（`state.field_not_writable`）。没有任何访问条目、也没有任何声明字段的 Profile 视为"尚未配置"，不约束任何键。返回结果带 `declarationConfigured`，区分"校验通过"与"无声明放行"。
- **声明存储**：`StateDeclarationRepository`（`user_dir/state-declarations/<name>.json`，原子写）+ `StateDeclarationService`（保存时拒绝重叠与非法名字）+ 4 个 Tauri 命令与前端路由；绑定解析沿用"聊天 → 角色/群组 → 无 fallback"；`materializeCurrentPromptSnapshot` 按解析结果注入 `stateDeclaration`，拿不到不放键。

**验收**：未声明字段与类型不符都被拒绝，错误可定位到 key；含错提交在一次运行内被修正。

### 阶段 2 · 注入

**要验证的假设**：注入位置对前缀缓存的实际影响。

**前置地基：求值不下沉，状态走后端**（2026-09-20 两次重推导后的结论）

原方案"世界书求值整体下沉到后端"已撤回。起因是目标澄清，且澄清了两次：

1. 下沉的目的不是"求值在后端"，而是**准入**——"让 AI 别做一件事的好办法，是别告诉它有这个事"；
2. 需要按 Agent 准入的对象也不是世界书，而是**状态切片**——动态条件不是世界书，用世界书条目承载状态变量（现状的扩展方案）是本次要废弃的错位。

状态系统（阶段 0/1）的真实目的由此确定：替换「世界书条目承载状态 + 模型输出 `<StatusPlaceholderImpl/>` 特定格式 + 正则抓取更新 HTML」的扩展方案——写入走 `state.update` 工具（强约束），状态切片由后端按 Profile / 条件算出并**推送注入**（模型不拉取，注入即准入），StateAccess 三态（注入 / 可见 / 可写）逐字段逐 Profile 配置，状态机层的脚本对状态做图灵完备处理。完整设计见 [StateInjection](StateInjection.md)。

由此，世界书**保持前端 JS 唯一实现**，不为状态服务、也不需要 per-Agent 门控。

**实现形态**：`StateAccess` 三态配置**存在 Profile 上**（`AgentProfileDefinition.stateAccess`，随画像文件持久化，保存时拒绝可覆盖同一字段的重复条目）；Run 启动时后端把该 Profile 的策略冻结进 run 输入（`stateAccess`），`state.update` 从那里读取并逐字段校验。按「注入」勾逐字段过滤后渲染（`tt-domain` 的 `models/state_injection.rs`）；落位按条目的 `injectSlot` / `injectDepth` 分层（默认 `atDepth` + 深度 4）；读数走聊天最新已提交版本（`WorkspaceRepository::read_persistent_state_file` + `get_state_injection` 命令 + `/api/state/injection` 路由）；前端在 `Generate()` 组装前用世界书同款扩展提示落位，生成结束随 `flushWIInjections` 一起清理。

**token 预算**：当前不裁剪，块数由「注入」勾的字段数决定；访问配置网格 UI 与 `injectSlot` 的编辑入口在声明编辑器里。

**动态覆盖静态不做在这里**：让状态去压过静态内容，本质是"多个来源争同一段提示词"的仲裁问题，与状态机的转移求值是同一类问题；等状态机落地时用它自己的机制表达（多出来的状态、条件与优先级），而不是在注入选址上再加一层规则。

**验收**（没有任何声明字段的聊天得到零块，因为 `render_injection` 直接短路）：

| 假设 | 结果 |
| --- | --- |
| 渲染出的 `键: 值` 文本足以支撑写回 | 模型只写了注入文本里见过的键，拼写完全一致 |
| 「注入即准入」真的挡住未注入的字段 | 声明但未注入的 `角色/艾拉/好感度` 未被触碰 |
| 增量语义在注入文本下仍成立 | 场景未改变的 `环境/日期` 没有被重复提交 |
| 思考模式不影响工具调用 | 端点返回 `reasoning_content`，工具调用照常 |

### 阶段 3 · 面板与配置界面

**要验证的假设**：面板在长聊天下确实是常数 DOM，且不引起重排；图片候选集 + 条件选择在日常使用里比"固定一张图"更省事而不是更麻烦。

**3a · 默认面板**：
- 域层：`models/state_panel.rs`——面板/栏/字段渲染模式、图片候选集与条件选择、按声明派生默认布局、保存期校验（候选顺序、图片来源与字符集、未注册 op）；`evaluate_condition`（单条件入口）与 `StateDocument::condition_fields`（条件字段适配）同期补齐，供面板、谓词条目与状态机共用。
- 配置归属：面板配置挂在**声明**上（`StateDeclaration.panels`），一份文件一条绑定链；声明保存时一并校验（重叠面板、无法兑现的候选集）。
- 数据接口：`get_state_panel(chatRef, stableChatId, declaration)` → `{ stateId, panels }`，读聊天最新已提交版本（与注入同一版本），路由 `/api/state/panel`。
- 前端：`state-panel-ui.js` 建左右停靠栏（类名契约 `tt-state-rail` / `tt-rail-left` / `tt-rail-right` / `tt-state-panel` / `tt-state-field`），`css/state-panel.css` 提供默认样式；`before`/`after` 之外的图片来源在渲染前再校验一次（背景值走 `url("...")`，非法源直接跳过）；刷新挂在 `chat_id_changed` 与 `generation_ended`，失败即清空（不留陈旧面板）。
- **楼层跟随**：面板读"最新已提交版本"就是正确语义。`syncSwipeToMes`（`script.js`）在切换 swipe 时把 `swipe_info[swipe_id].extra` 复制进 `message.extra`，因此落盘 payload 里 `persistStateId` 本来就是**当前选中 swipe** 的状态。`refreshStatePanel` 先 `flushDebouncedChatSave()` 再读（读之前先落盘），并订阅 `chat_id_changed` / `generation_ended` / `MESSAGE_SWIPED` / `MESSAGE_SWIPE_DELETED` / `MESSAGE_DELETED`。
- **边界**：`state_get_floor`（按指定楼层读状态）没有做，也暂不需要——聊天界面没有"停留在某个历史楼层"的概念，面板始终显示故事当前状态。

**3b · 面板配置界面**：宿主是既有的第一方 UI 根 `src/scripts/extensions/agent-system/src`（该根已受 rspack / tsconfig / eslint / rstest / 第一方 UI 守卫覆盖，新增独立 UI 根要动九处配置）。

数据层 `state-config-model.ts`（声明草稿模型、宿主机路径校验、空白行归一、形状问题列表）与 `state-config-api.ts`（走既有 `/api/state-declarations/*` 路由）；**声明编辑器**——面板应用的 `state` 页签（`PANEL_TABS`），`state-config-ops.ts` 的纯编辑操作 + `state-config-controller.ts`（未保存改动守卫、脏标记、新建/保存/删除、切页签只刷新列表不覆盖草稿）+ `StateConfigPanel.tsx`，覆盖声明字段表（键模式 + 显示名）、面板（标题 / 左右栏 / 匹配键）、面板字段（键模式 / 显示名 / 文本或图片渲染）与图片候选集（来源 + 逐张条件字段 / op / 值，面板背景与字段图共用同一编辑器）。编辑期的形状问题就地列出；语义规则（重叠面板、候选集顺序、未注册 op）由保存调用回答，消息原文呈现。列表比较条件（`in` / `not_in`）按 op 分流保存 `values`，单值比较保持 `value`。

**3b 续**：**访问配置网格**（Profile 三勾矩阵，含批量粘贴、从已保存声明 / 当前聊天绑定声明展开、按类别折叠）、**状态机编辑器与求值预览**（`Machines` 页签）、**条件组合与条件脚本**（`all` / `any` / `not`、共享模块表 `panels.scripts`）与**三处功能引导与起步示例**（新建即预填默认名与可用示例）。`STATE_CONDITION_OPS` 目前照抄域层内建注册表，注册表扩容时需要同步（真源仍在后端）。

**3c · 自定义样式**：三级样式叠加，后一层只写与前一层不同的部分。

- **Level 1 主题 CSS**：存在声明的面板配置里（`panels.css`）。编辑器用 `@adobe/css-tools` 解析它，并**在保存时**给每个选择器加上 `.tt-state-root` 前缀（`html` / `body` / `:root` 视作面板根），**编译产物才是存储内容**——于是渲染期零解析，渲染层只是把这段文本贴进一个 `<style>`（在默认样式之后，层叠顺序即层级）。只允许普通规则与 `@media` / `@supports` / `@keyframes`；`@import`、`@font-face` 这类"让面板自己去抓资源"的写法按名字拒绝。域层**不解析样式表**：它只做机械校验——长度上限、`<`、`@import`，以及每个 `url()` 必须是宿主路径（与图片同一条规则）。语法错误按行列报告，未编译成功时编辑器拒绝保存，不会把半份主题存下来。
- **Level 2 HTML 模板**：每个面板可以自带一段标记（`StatePanelSpec.markup`——名字取它**是**什么：一棵元素与绑定的树，不是留给谁去求值的模板）。编辑器用 `DOMParser` 解析、按白名单走一遍，并**在保存时编译成节点树**；域层再验一次这棵树（标签与属性都必须是渲染器认识的白名单成员、绑定必须命中声明里的**某一个**字段、节点数 / 层数 / 单段文本长度有上限）；渲染器只做 `createElement` / `setAttribute` / `textContent`——**从不由值生成标记**，所以运行期没有可解析的东西。安全与作用域都不依赖字符串清洗：编辑器解析一次，域层验树一次，渲染器只按树创建。
  - **绑定词汇表**：`{{value 键}}`（字段值按文本插入，多个值逗号连接）与 `{{#if 键}}…{{else}}…{{/if}}`（字段有值取 then，否则 else）。**没有 raw 标记绑定**：值在渲染期才到达，把它当标记插入就意味着在渲染期清洗——正是本设计禁止的渲染期解析，因此 `{{raw …}}` 按名字拒绝，而不是被悄悄忽略。绑定只能用字面键：`角色/*/好感度` 这类模式覆盖多个键，"你要的是哪一个"是模板在渲染期回答不了的问题，保存时拒绝。
  - **模板替换的是面板体**：`__header` 与 `__body` 仍在，模板内容画进 `__body`（取代默认字段行），因此 Level 0 的类名契约与 Level 1 的主题对模板化面板继续生效。
  - **文档只存编译结果**，所以打开一份已保存的声明需要反向：`printTemplate` 把树打印回文本供编辑，"保存 → 重开"是一个往返（两侧各有用例守着，包括"打印回来还能编译成同一棵树"）。

**验收**：万级楼层下面板 DOM 数为常数；滚动与加载不触发聊天容器重排；切换或删除楼层后面板立即反映；同一状态在不同条件下选中不同候选图，且图形来源无法越出宿主路径。

### 阶段 4 · 执行者与强制调用

**实现形态**：

- **推进侧（状态机接线）**：按聊天绑定机器并把完整 spec 随 run 输入冻结；位置持久化在 `state/machine.json`（与状态文档同根，随楼发布、由下一楼继承）；模型侧工具 `state.transition`（请求经 `resolve_requests` 解析，写入先过声明与可写授权再动位置）；Run 提交时自动求值（只跑规则自触发的转移，失败记入 run journal 但不带走已提交的正文）；**绑定入口**——声明与机器各在自己的页签里可绑定到当前聊天或当前角色/群组，绑定数据仍是既有的 `chat_metadata` / `power_user` 容器（界面只做选择，写入由页面运行时完成）。
- **消费侧**：不新增执行者配置——**谁有可写字段谁就是执行者**，这与"注入即准入"是同一条规则；"有可写但未提交时标记该楼"由后端在楼层 metadata 写入 `stateUpdated: false`（判据是**状态文档是否变化**，不是工具是否被调用），面板在标题栏显示标记。
- **强制调用不做**：它会让模型提交"没有变化"的字段，与增量语义冲突，且最后一轮要与 `workspace.finish` 争夺出口。

**验收**：没有可写字段时不产生任何额外调用；有可写但未提交时该楼被标记，面板可显示"未更新"。

### 阶段 5 · 状态谓词条目

**内容**：条目组、谓词、可用性前提、效果与标签；四阶段确定性求值并输出逐条判定原因；求值预览界面；永不落盘。

**实现形态**：

- **引擎与校验**：`tt-domain/models/state_predicate.rs`（恒常条目、组内限定选择、谓词过滤、可用性前提；原因逐条记录）。
- **存储与接口**：`state-predicates/`，命令与 `/api/state-predicates/*` 路由（含 `/evaluate`——把假定的字段值建成状态文档后走与组装同一条求值路径，供编辑器预览未保存的草稿）；聊天级求值命令 `get_state_predicate_entries`（绑定策略与声明同构，组装配额豁免、超限截断记 `truncated`）。
- **前端落位**：`state-predicate-entries.js`（atDepth 4、独立键前缀 `tauritavern_state_predicate_`、独立 flush）与绑定 kind `state_predicates`（`toggleStatePredicateBinding`）。
- **编辑器与预览**：`Predicates` 页签——组（互斥、优先级、平局按声明顺序）、常驻条目、标签、inhibit/require 作用、可选前提；预览按假定字段值列出被注入的条目及正文，被排除的逐条带原因。组合条件按原样透传，本编辑器不编辑组合。

**验收**：同一配置重复求值结果一致；预览能逐条显示被移除的原因（不可用 / 被抑制 / 组内未选中）。

### 状态机层（正交，独立排期）

[状态机](StateMachine.md)不在这六个阶段里，它是叠在状态文档之上的**可选层**：本篇的阶段 0–5 是"值怎么存、怎么注入、怎么显示"，状态机是"位置怎么走"。两者共用同一份声明与同一个 `state` 持久根，但状态机的进度不阻塞本篇任何阶段，本篇的阶段也不依赖它。

它与本篇的交集只有两处，已在上面的阶段里标出：阶段 3 的机器编辑器，阶段 4 的推进接线（绑定与快照注入、位置持久化、`state.transition`、Run 提交时自动求值）。

## 现状与动机

当前状态栏由第三方扩展实现：提示词要求模型在回复正文里输出特定格式标记（如 `<StatusPlaceholderImpl/>`），扩展用正则从正文抓取、解析，再更新 HTML 状态栏（如"生成回复中 | 已消耗 ◇ 169"）。状态变量本身由世界书条目承载。本仓库内没有对应实现。

该做法有三个问题：

1. **协议错位**：结构化事实被编码成自然语言 token 流，再用正则解回来。模型措辞、换行、全角半角一变就需要重写规则。
2. **没有判据**：模型漏字段、被截断或复述旧值时，渲染层无法判断"该不该接受这次更新"。正则只能报告解析失败。
3. **成本随楼层线性增长**：状态块是消息内容的一部分，N 楼就有 N 份面板，且每份在挂载时都要解析一次；虚拟化能减少 DOM，救不了解析。

已有的持久工作区机制提供了持久、版本、按 Profile 的作用域与消息绑定，但它的内容以散文形式存储，只能被工具拉取、不能推注入，且没有写入校验。本文的设计把状态定义成"由用户声明、由模型填写、按字段授权"的条目集合，从而复用两侧能力，同时得到注入、校验与显示。
