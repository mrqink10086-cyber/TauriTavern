# 状态注入与可见性（StateInjection）

> 本文取代已删除的 PerAgentWorldBooks.md——门控的对象想错了：需要按 Agent 准入的是**状态切片**，不是世界书。动态条件不是世界书；用世界书条目承载状态变量，是要废弃的错位。

## 一、要替换的是什么

现状（实证）：状态栏由扩展实现——提示词要求模型在回复里输出特定格式标记（如 `<StatusPlaceholderImpl/>`），扩展用正则从正文抓取、解析，再更新 HTML 状态栏（如"生成回复中 | 已消耗 ◇ 169"）。状态变量本身由世界书条目承载。

这个方案的根本问题：

1. **弱约束**：让模型稳定输出特定格式是劝出来的，不是管出来的——漏输出、格式漂移是常态，强约束也不保证遵守。
2. **正则脆弱**：格式一变，规则就失效。
3. **载体错了**：世界书是"按关键词检索注入资料"的机制，不是运行时数据结构。拿它承载状态，激活、更新、校验全部被迫借用世界书的语义。
4. **无准入**：所有 Agent 看到同样的状态内容，无法按 Agent / Profile 裁剪。

## 二、替换方案：阶段 0/1 已建的地基

- **状态 = 后端一等数据**：结构化文档存 `state/` 工作区，按楼版本化，swipe 分叉各自独立。
- **写入走工具**：模型用 `state.update` 写——schema 强约束、声明校验（未声明的键拒绝）、批量报错回灌一轮改对；不再让模型输出格式文本。
- **注入走推送**：状态切片由后端按 Profile / 条件算出，**动态注入**提示词——模型不拉取。**注入即准入**：没注入的字段，模型不知道它存在——"让 AI 别做一件事的好办法，是别告诉它有这个事。"
- **可见性按 Profile 配置**：StateAccess 三态（**注入 / 可见 / 可写**）逐字段逐 Profile——同一字段可以 A Agent 注入、B Agent 仅 UI 可见（状态栏显示但不进提示词）、C Agent 完全不可见；并可附加各种条件。
- **脚本图灵完备**：状态机层（QuickJS 钩子 + 比较器 / 动作注册表）对状态做任意处理，多状态可组合成复杂状态机。
- **状态栏 UI 从数据接口读**：前端从后端读状态数据渲染状态栏，正则抓取方案废弃。

## 三、世界书的位置

世界书**保持前端 JS 唯一实现**，不为状态服务，也不需要 per-Agent 门控（那是状态的需求，不是世界书的）。状态数据的宿主在后端（`state/`），状态切片的计算天然在后端（纯规则、可测、可版本化）；注入的**落位**（插到哪条消息前后、深度等）由前端在组装提示词时按既有机制完成——数据从后端来，位置由前端定。

为"世界书求值下沉"建的 Rust 链因此无人使用（清单见 [State.md](State.md) 阶段 2 前置地基）。

## 四、与 State.md 阶段 2 / 5 的关系

- 阶段 2 的四项内容就是本文第二节的落地：注入过滤 = StateAccess「注入」勾；访问配置网格 = StateAccess 配置界面；频率分层与动态覆盖静态是注入策略。
- 阶段 5 的状态谓词作用在**状态数据**上（决定某个状态条是否注入），不是把状态变成世界书条目。
